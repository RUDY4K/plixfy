# التشغيل المستمر لفريق Plixfy

## النموذج

`plixfy-manager` هو المدير الوحيد وصاحب الحالة والطابور. الفريق دائم من ناحية
الأدوار والهدف والذاكرة، بينما الوكلاء التنفيذيون يُنشؤون لكل دورة عمل ثم
ينتهون بعد تسليم نتيجة قابلة للتحقق. هذا يمنع استهلاك الموارد في جلسات خاملة
ويجعل كل مهمة ذات نطاق وصلاحية وميزانية واضحة.

الهدف المستمر مفعّل داخل جلسة المدير. لا يعني ذلك أن عملية محلية أو جهازًا
سيبقى عاملًا إذا أُغلق Berd أو انقطع الجهاز أو الشبكة. التشغيل غير المراقب خارج
الجلسة يحتاج مشغّلًا موثوقًا مستقلًا، ولا يُفعّل قبل اختبار العزل والميزانية.

## دورة المدير

1. يقرأ مؤشرات الصحة والطابور والقرارات السابقة.
2. يستخرج الأعمال المستحقة ويمنع التكرار عبر `dedupe_key`.
3. يعيّن وكلاء ضيقين بملكية غير متداخلة، بحد تزامن تقني لا يقيّد العدد الكلي.
4. يجمع النتائج ويطلب مراجعة مستقلة لكل عمل متعدد الوكلاء أو يتضمن كتابة.
5. ينفذ الأعمال الآمنة القابلة للتراجع، ويضع الأفعال الحساسة في
   `waiting_approval`.
6. يحدّث الحالة ويقدّم للمالك تقريرًا واحدًا واضحًا.

## إيقاع العمل

- كل ساعتين: صحة الإنتاج والمسارات الأساسية و`ads.txt` و`robots.txt` وsitemap
  وآخر نجاح للأتمتة.
- كل 6 ساعات: فرز الحوادث والتراجعات والطابور وإعادة المحاولة المستحقة.
- يوميًا: GA4 وSearch Console المجمعة، SEO، الكتالوج، مسودات المحتوى، وتحليل
  مسار اللعب.
- ليليًا: العربية والإنجليزية، الجوال والكمبيوتر، الأداء، الوصول، وتدفق اللعب.
- مرتان أسبوعيًا: الإيرادات والامتثال الإعلاني وأثر الإعلانات على UX.
- أسبوعيًا: تقرير مجلس إدارة يقارن النتائج بخط الأساس المثبت.
- شهريًا: مراجعة الاستراتيجية والتجارب والأولويات.

الجدولة Catch-up: إذا فات موعد، تُشغّل أقرب دورة مستحقة مرة واحدة ولا تُكرر
المهمة بسبب تأخر المشغّل.

## الحالات والتعافي

حالات المهمة: `ready`, `running`, `review`, `waiting_approval`, `blocked`,
`done`, `quarantined`.

- لكل مهمة أساس Git وملكية ملفات ومدة lease وheartbeat عند توفر مشغّل دائم.
- إعادة المحاولة بعد 5 ثم 15 ثم 60 دقيقة.
- بعد ثلاث محاولات للسبب نفسه يعمل circuit breaker وتصبح المهمة `blocked`.
- عند حادث P0 تتوقف أعمال الكتابة والنمو التي يديرها `plixfy-manager`؛ تستمر
  المراقبة والتشخيص فقط. لا تشمل هذه القاعدة workflows القديمة الخارجة عن
  تحكم المدير حتى يحسم المالك تفويضها أو تحويلها إلى dry-run/manual.
- أي patch يبقى `review_required` عند تغير الأساس أو قبل الدمج.
- لا ينشئ الوكلاء وكلاء آخرين؛ كل التفويض يمر عبر المدير.

## ما يعمل تلقائيًا

- المراقبة والقراءة والتحليل والبحث العام الموثق.
- قراءة مؤشرات مجمعة بلا بيانات شخصية.
- المسودات المحلية وdry-run بلا شبكة أو أسرار.
- patches معزولة قابلة للتراجع، مع الاختبارات المتاحة أو توثيق ما تعذر
  تشغيله، ومراجع مستقل.

## ما يتوقف للموافقة

- push وmerge وdeploy وrollback وتغيير workflows الإنتاجية.
- أي منشور أو مقال عام أو رسالة أو Telegram أو Discord أو IndexNow.
- الإعلانات والميزانيات والأسعار والاشتراكات والاستدعاءات المدفوعة.
- الحسابات والاعتمادات والأسرار والموصلات الجديدة.
- حذف ملفات أو بيانات أو الكتابة في قاعدة بيانات الإنتاج.

## شرط التفعيل الخارجي

قبل تشغيل Orchestrator غير مراقب: محاكاة 72 ساعة، منع تشغيل مديرين معًا، تعافٍ
من انقطاع العملية، صفر وصول للأسرار، عدم لمس checkout المتسخ، عزل كل كتابة،
فشل مغلق لكل أثر خارجي، واختبارات عربية/إنجليزية وجوال/كمبيوتر.

كل دورة تحتاج ميزانية عقد محددة. يتوقف إنشاء دورات جديدة عند غياب الميزانية أو
تجاوزها، ويظل المشغّل غير المراقب معطلًا حتى يعتمد المالك سقفًا يوميًا واضحًا.
الطابور لا يتجاوز 20 مهمة مفتوحة وتنتهي المهمة غير المتجددة بعد 7 أيام.
