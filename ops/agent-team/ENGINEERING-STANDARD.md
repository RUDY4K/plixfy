# معيار الهندسة والتسليم في Plixfy

هذا هو أسلوب العمل الافتراضي لكل تعديل في الموقع أو البيانات أو الأتمتة. الهدف
أن تكون كل نتيجة مفهومة وقابلة للاختبار والصيانة والرجوع، مع حفظ تغييرات المالك.

## المبادئ

- يبدأ العمل من دليل ومصدر حقيقة محدد، لا من التخمين أو نسخة محلية قديمة.
- لكل مكوّن مسؤولية واحدة وواجهة واضحة، ولكل معلومة مصدر حقيقة واحد.
- يكون التغيير أصغر نطاق يحقق الهدف، من دون إعادة هيكلة لا تخدمه.
- نجاح الأمر أو الـworkflow ليس دليلًا على نجاح النتيجة؛ تُفحص النتيجة نفسها.
- لا تُخفى الأعطال كنجاح، ولا تُستخدم البيانات غير المتاحة بوصفها صفرًا.

## بوابات التسليم الإلزامية

تطابق العلامات داخل هذه القائمة `policy.json` حرفيًا ويتحقق منها البرنامج:

1. <!-- delivery-gate:source-of-truth --> **مصدر الحقيقة:** أحدث `origin/main`
   وحالة الإنتاج والبيانات الأحدث، مع تسجيل `base_commit` وحالة checkout المحلي.
2. <!-- delivery-gate:scope-and-acceptance --> **الهدف والنطاق:** سلوك قبل/بعد،
   معيار قبول قابل للقياس، وما يقع خارج النطاق.
3. <!-- delivery-gate:exclusive-ownership --> **الملكية:** مسؤول واحد لكل جزء
   ومسارات كتابة دقيقة وغير متداخلة.
4. <!-- delivery-gate:isolated-worktree --> **العزل:** فرع وworktree منفصلان من
   المصدر الصحيح، مع بصمة تثبت بقاء ما يقع خارج الملكية دون تغيير.
5. <!-- delivery-gate:implementation --> **التنفيذ:** وحدات صغيرة، أسماء واضحة،
   ثوابت مشتركة، وأخطاء قابلة للرصد.
6. <!-- delivery-gate:targeted-verification --> **التحقق الموجّه:** اختبار العطل
   أو السلوك المتغير، ثم الحزمة المرتبطة به.
7. <!-- delivery-gate:full-verification --> **التحقق الكامل:** `npm test` و
   `npm run build`، مع AR/EN والجوال وسطح المكتب عندما يتأثر أي منها.
8. <!-- delivery-gate:independent-review --> **المراجعة المستقلة:** مراجع لم يكتب
   التغيير يفحص commit المرشح نفسه. لا يمر P0 أو P1 مفتوح.
9. <!-- delivery-gate:local-preview --> **المعاينة المحلية:** تُفحص نسخة محلية أو
   بيئة آمنة لا تحتاج أثرًا خارجيًا قبل طلب أي دفع إلى المستودع.
10. <!-- delivery-gate:external-approval --> **الموافقة الخارجية:** push أو Vercel
    Preview أو merge أو deploy أو نشر أو إرسال أو إنفاق يحتاج موافقة المالك على
    الإجراء نفسه. إذا احتاجت Preview إلى push، تأتي موافقة push أولًا، ثم تُفحص
    Preview، وتبقى موافقة نشر الإنتاج بوابة مستقلة ما لم تشملها الموافقة صراحة.
11. <!-- delivery-gate:production-verification --> **الإنتاج والرجوع:** بعد النشر
    يُفحص السلوك والقياس والملفات الحرجة ويُحفظ commit يمكن الرجوع إليه.
12. <!-- delivery-gate:run-record --> **سجل التشغيل:** يسجل المدير حالة كل بوابة
    ودليلها وأوامر التحقق وأكواد الخروج في `engineering-evidence`.

حالة البوابة إما `pass` أو `not-applicable` مع سبب محدد. إذا تغير أي ملف بعد
المراجعة، تعاد الفحوص المتأثرة وتُراجع النسخة الجديدة قبل الدمج.

## حدود البنية

- **البيانات:** جلب البيانات والتحقق منها والتطبيع؛ لا منطق عرض.
- **النطاق:** قواعد الألعاب والمحتوى والفهرسة والقياس؛ بلا اتصال مباشر من العرض.
- **الواجهة:** العرض والتفاعل وRTL والوصول؛ تستهلك عقودًا واضحة من طبقة النطاق.
- **التكاملات:** لكل تكامل خارجي مهلة وحدود retry وحالة فشل ظاهرة.
- **التشغيل:** workflows والصحة والسجلات؛ لا تمنح صلاحية نشر ضمنية.

قبل تعديل Next.js، تُقرأ الوثيقة المناسبة من `node_modules/next/dist/docs/`
لهذه النسخة. لا تُستخدم افتراضات من إصدارات أقدم.

## جودة الكود والبيانات

- لا أعداد أو تواريخ يدوية عندما يوجد مصدر بيانات فعلي.
- لا تكرار لقواعد الفهرسة أو أحجام الصفحات أو أسماء الأحداث؛ تستخدم دالة أو ثابتًا
  مشتركًا.
- الجدولة والنشر قابلان لإعادة التشغيل بلا تكرار أثر، ولهما مفاتيح dedupe.
- فشل الدليل أو الموافقة أو سلامة البيانات يغلق العملية ولا ينشر بديلًا ضعيفًا.
- أي retry محدود، ولا يعيد عملية مالية أو منشورًا دون idempotency مثبتة.

## مصفوفة التحقق

| نوع التغيير | الحد الأدنى |
|---|---|
| منطق أو إصلاح | اختبار يثبت الحالة قبل/بعد + الحزمة المرتبطة |
| واجهة | AR/EN، ‏390px و1440px، لوحة مفاتيح، وعدم overflow |
| لعبة أو كتالوج | المصدر والعدد وdedupe والأجهزة وصفحة تشغيل فعلية |
| محتوى أو SEO | المصدر والحقوق واللغة وcanonical/hreflang/robots وsitemap |
| قياس | الموافقة وdedupe واسم الحدث والمصدر والوسيط |
| تكامل أو workflow | dry-run آمن وtimeout/retry وحالة الفشل وإيصال التشغيل |
| إصدار | الاختبارات الكاملة والبناء وPreview ثم فحص إنتاج حي |

لا تُكتب اختبارات تنسخ التنفيذ حرفيًا؛ تختبر الحدود والمخاطر التي قد ترجع.

## الإنفاذ في مسارات التنفيذ

- مسار CLI يفرض worktrees مؤقتة وملكية دقيقة وبصمات المصدر تقنيًا.
- مسار وكلاء Codex الأصلي ينفذ كل كتابة مادية في worktree مستقل أيضًا. يسجل
  المدير مساره و`base_commit` والملكية وبصمة checkout المصدر قبل الدمج وبعده.
- تحديثات الذاكرة وحدها يكتبها المدير، لكن تنفيذ الكود الذي تنتج عنه يبقى في
  worktree. لا يدمج المدير من شجرة مصدر متسخة.
- كل سجل جديد أعلى علامة `legacy-runs-below` في `RUNS.md` يحتاج كتلة
  `engineering-evidence` كاملة، ويرفض المدقق السجل الناقص.
- المساحة المحكومة في `RUNS.md` مخصصة لسجل التسليم النشط. قبل بدء تسليم جديد
  ينقل المدير السجل السابق أسفل علامة `legacy-runs-below`، ولا يحذف worktree
  المسجل حتى انتهاء التحقق النشط وأرشفة السجل.

## قواعد Plixfy الثابتة

- بيانات الكتالوج الأحدث المنشورة هي مصدر الحقيقة؛ لا تستبدل بالأقدم.
- الفهرسة للمحتوى المراجع فقط، ولكل لغة موافقة مرتبطة ببصمة المحتوى والدليل.
- `ads.txt` يطابق حساب Plixfy الموثق فقط.
- التحليلات لا تعمل قبل الموافقة، وأحداث اللعب لا تُضاعف.
- تبقى CSP في Report-Only حتى اختبار فرضها على Preview وإغلاق المخالفات المؤكدة.
- لا يغير وكيل DNS أو إعلانًا أو ميزانية أو بيانات اعتماد أو إنتاجًا بلا موافقة
  صريحة على الإجراء نفسه ونطاقه.

## تعريف الاكتمال

المهمة مكتملة فقط عند وجود هدف ومصدر حقيقة وdiff محدود واختبارات ناجحة ومراجعة
مستقلة عند التغيير المادي وPreview عند الإصدار وموافقة لازمة وفحص إنتاج بعد
النشر وسجل قرار ومالك وموعد لأي بند متبقٍ. غير ذلك يسمى بوضوح: مسودة، مكتمل
محليًا، ينتظر موافقة، أو متعطل بسبب محدد.
