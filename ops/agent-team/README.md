# فريق وكلاء Plixfy

هذه طبقة إدارة عملية لمشروع Plixfy داخل Codex. يتعامل المالك مع مدير واحد،
والمدير يختار وكلاء متخصصين لكل مهمة ويجمع نتائجهم في تقرير موحّد.

## التكوين

- مدير واحد: `plixfy-manager`.
- 9 أدوار أساسية داخل `roles/` تمثل نقطة البداية، وليست حدًا أعلى.
- يحق للمدير إنشاء أي عدد من الوكلاء الدقيقين الإضافيين حسب المهمة.
- وضع افتراضي حسب المهمة، مع وضع تشغيل مستمر موثق في
  `CONTINUOUS_OPERATIONS.md`: المدير دائم الحالة والوكلاء يعملون بدورات محددة.
- مراجعة جودة إلزامية قبل إغلاق أي مهمة متعددة الوكلاء.

## طريقة التشغيل

تطبيق Codex Desktop هو الواجهة الأساسية. افتح مشروع `plixfy-new` واكتب الهدف
فقط؛ لا تحتاج PowerShell أو JSON أو تحديد عدد الوكلاء وأنواعهم. مثلًا:

> ابدأ مشروعًا لتحليل انخفاض الزيارات وتحسينها.

أو للتنفيذ:

> نفّذ تحسين صفحة الألعاب، وحافظ على تغييرات المستخدم الحالية.

يبتكر المدير التخصصات والعدد من الهدف وسياق المشروع، ثم ينفذ ويختبر ويراجع.
الصلاحيات تتبع الفعل لا اسم الوكيل؛ لذلك يستطيع وكيل تسويق البحث وكتابة مسودة
تلقائيًا، لكنه يتوقف قبل النشر الخارجي حتى يوافق المالك على الوجهة والمحتوى.

## ملفات الذاكرة

- `PROJECT.md`: الحقائق والأهداف والحدود طويلة الأجل.
- `ENGINEERING-STANDARD.md`: بوابات الهندسة والتسليم وتعريف الاكتمال.
- `STATE.md`: الحالة الحالية والمهام المفتوحة.
- `PERMISSIONS.md`: تعريف الصلاحيات وبوابات الموافقة والعزل.
- `ROUTING.md`: أمثلة تفكيك الأعمال إلى وكلاء دقيقين.
- `INTAKE.md`: حقول استقبال موحدة قبل التفكيك، ومنها تشخيص انخفاض الزيارات.
- `policy.json`: السياسة المركزية التي يفحصها البرنامج آليًا.
- `ROLE_TEMPLATE.md`: عقد إلزامي لأي دور ديناميكي جديد.
- `DECISIONS.md`: سجل القرارات المعتمدة.
- `RUNS.md`: سجل تشغيل الفريق والأدلة.
- `TASK_TEMPLATE.md`: عقد المهمة الذي يرسله المدير لكل وكيل.

## الوضع الآمن الافتراضي

الوكلاء يبدأون قراءةً فقط. ملفات Markdown لا تفرض الصلاحيات تقنيًا؛ لذلك لا
يُسمح لوكيل كتابة أو نشر بالعمل إلا إذا حدّد المدير العزل ومسارات الكتابة وبوابة
الموافقة في عقد التشغيل. وجود أمر نشر في `package.json` لا يعني السماح بتشغيله.

## التحقق

```powershell
npm run agents:check
```

هذا الفحص يتأكد من وجود المدير ومكتبة الأدوار الأساسية والذاكرة وقواعد
الصلاحيات وعقد كل دور ديناميكي. العدد الفعلي للوكلاء يحدده المدير عند كل تشغيل.

في الوضع المستمر، راجع `WORKSTREAMS.md` و`continuous-policy.json`. لا يعني
الاستمرار حلقة نموذج لا تنتهي؛ كل دورة لها هدف وميزانية ومراجعة، ثم يوقظ المدير
الدورة التالية عند استحقاقها.

## المشغّل الآمن

فحص العزل الفعلي:

```powershell
npm run agents:doctor
npm run agents:codex:doctor
npm run test:agent-team
```

يفحص الأمر الثاني نسخة Codex Desktop الموقعة مباشرة من مجلد تثبيت التطبيق؛
لا يعتمد على وجود `codex.exe` في `PATH` داخل PowerShell.

تجربة محلية بلا استدعاء نموذج:

```powershell
npm run agents:example
```

لجعل المدير يحدد الوكلاء ثم يشغّلهم فعليًا عبر Claude بلا أدوات:

```powershell
node scripts/agent-team-cli.mjs start `
  --request ops/agent-team/examples/launch-request.json `
  --adapter claude --confirm-public-model-egress
```

`--confirm-public-model-egress` إقرار تشغيلي محدد بأن الملفات الموجودة في
`allowedInputs` وسياق المدير الثابت (`PROJECT`, `ROUTING`, `INTAKE`,
`PERMISSIONS`, `ROLE_TEMPLATE`) عامة ويمكن إرسالها إلى مزود Claude. ترتبط
الموافقة ببصمات محتوى هذه الملفات وبالطلب والنموذج المحدد؛ ثم يشتق المشغّل
إيصال تنفيذ مرتبطًا بالعقد وmanifest الـsnapshot والنموذج. لا يمكن تغيير النموذج
عن الموجود في ملف الطلب. إيصالات النموذج قصيرة العمر، ذات nonce، وتُستهلك مرة
واحدة داخل عملية CLI؛ ولا يستطيع مستدعي مكتبة JavaScript تشغيل النموذج الحقيقي
خارج مسار `start`. لا يوجد خيار
لعدد الوكلاء؛ المدير يحدد العدد، بينما `maxConcurrency` يحدد التزامن اللحظي فقط.
كل الحالة والإيصالات تحفظ تحت مجلد النظام المؤقت، لا داخل المشروع.

سياق المدير و`allowedInputs` يمران كلاهما عبر وسيط snapshot نفسه وفاحص الأسرار
قبل إنشاء prompt. ويكتب المشغّل `final-receipt.json` بحالة `failed` حتى إذا وقع
الفشل أثناء التخطيط أو التحقق المسبق أو إنشاء snapshot.

يتحقق المضيف من منشأ الدليل وبصمته وموقعه ونص الاقتباس، لكنه لا يدّعي أنه فهم
دلالة الادعاء آليًا. لذلك تبقى نتيجة النموذج `modelVerdict` استشارية، وينتهي
التشغيل الناجح تقنيًا بالحالة `review_required` إلى أن يراجع المالك النتيجة.

## تنفيذ تعديلات برمجية معزولة

هذا مسار طرفية اختياري لتعديلات المستودع المعزولة، وليس واجهة الفريق العامة.
اكتب الهدف فقط، وسيختار مدير النطاق ملفات
القراءة والكتابة الآمنة من ملفات Git العامة ثم يسلّمها لمدير الوكلاء:

```powershell
npm run agents:auto -- "حسّن صفحة الألعاب وأصلح المشاكل المرتبطة بها"
```

لا يقرأ الاكتشاف محتوى المستودع كله؛ يرسل أسماء الملفات العامة وأحجامها فقط،
ثم تمر الملفات المختارة عبر فحص الأسرار والعزل المعتاد. الملفات المتسخة وملفات
الأسرار وCI والنشر والاعتماديات ونظام الوكلاء لا تكون أهداف كتابة تلقائية.

للاستخدام المتقدم فقط، يمكن تعديل `examples/code-request.json` يدويًا لتثبيت
`allowedInputs` و`writeScope` بدقة. يجب ألا تكون الملفات المستهدفة معدلة حاليًا
في checkout الرئيسي.

```powershell
npm run agents:code:check

npm run agents:code:start
```

الأمر الثاني هو الصيغة الموصى بها في PowerShell؛ يتجنب مشاكل backtick والشرطة
المائلة، ويستخدم `examples/code-request.json` مع Codex تلقائيًا.

يقرر المدير عدد الوكلاء وتوزيع الملفات بلا حد إجمالي ثابت. يعمل كل منفذ في
worktree مؤقت منفصل ومثبت على `HEAD`، ولا يرى shell أو الشبكة أو أسرار الجهاز.
تكون النتيجة قائمة بملفات `.patch` وبصماتها ومسارات worktrees للمراجعة. لا يمس
المشغّل checkout الرئيسي، ولا يدمج أو ينشئ commit أو يدفع أو ينشر. طبّق patch
يدويًا فقط بعد مراجعته؛ وتبقى النتيجة `review_required`.

v2.0 يدعم ملفات نصية وعمليتي `create` و`replace` فقط. تغيير dependencies أو
ملفات CI والسياسات وملفات نظام الوكلاء محظور. كما أن تشغيل اختبارات المشروع
مؤجل حتى يتوفر runtime Linux معزول؛ يراجع QA الـpatch لكنه لا يدّعي نجاح tests.
ولمنع تنفيذ أوامر من Git نفسه، يعزل الوسيط بيئة Git ويعطل السمات العامة
و`textconv`، ويرفض المستودعات التي تستخدم submodules أو checkout filters أو
ملف `.git/info/attributes` غير فارغ أو إعدادات Git محلية تتضمن ملفات أخرى.

`codex` هو المزود الافتراضي لمسار الكتابة ويستخدم تسجيل دخول ChatGPT الموجود
في تطبيق Codex؛ لا يحتاج حساب Claude. يبقى `--adapter claude` خيارًا مستقلًا
فقط لمن لديه دخول Claude Code مؤهل أو فوترة API، ويجب عندها اختيار نموذج Claude
في ملف الطلب.
